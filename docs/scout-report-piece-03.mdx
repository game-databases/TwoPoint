Reading of the spaces (ground-truthed in §6): plot `Bounds` is
world-space centre/extent; room `Anchor` is grid cells, `WorldPosition`
is world units, `Tiles._saveData` is a row-major w×h occupancy bitmap
(values observed 0/1); item `LocalPosition` is relative to its owning
room's `WorldPosition` (sample: room at x −152 + item local 17 ⇒ world
−135, inside the room's tiles), `LocalRotation` is degrees.

**Join coverage probe:** indexing every exported
`GameItem{,Lite,Variation}Definition` by `(bundle, pathId)` (7 bundles,
3,779 entries) and resolving all 22,996 scenario item `Definition`
PPtrs same-file: **22,210 resolve (96.58%)**; 786 residue concentrated
in cross-file references (`Wanted` 14, `Super_Built_Up` 2, `FreePlay_
BuiltUp` 6, `Ghosts` 69, …). The sample record resolves end-to-end:
pathId `522383310774550334` → dump `Item_Door_Building_Moonbase_Main`,
whose `_id` = **−572923782 = the ItemRecord's `DefinitionID`**. So
`ItemSaveData.DefinitionID` ≡ `ScriptableObjectWithID._id` ≡ the numeric
key the stub layer does not currently emit (G3).

## §7 Coordinates and units — which space each datum lives in

| Datum | Source | Space | Units / convention |
|---|---|---|---|
| `WorldBounds` | LevelConfig (28) | world | metres-like Unity units; box 400×400×32 centred origin |
| `SpawnPoint` | LevelConfig | world | (−66, 0, −24) |
| `PlotRecords[].Bounds` | LevelScenarioV2 | **world** | centre+extent (Unity `Bounds`) |
| `RoomRecords[].WorldPosition` | LevelScenarioV2 | **world** | position of the room's tile-grid origin |
| `RoomRecords[].Anchor`, `Tiles` bitmap | LevelScenarioV2 | **grid cells** | 2.0 world units/cell; row-major w×h 0/1 occupancy |
| `ItemRecords[].LocalPosition` / `LocalRotation` | LevelScenarioV2 | **room-local** world units / degrees CW | add owning room's WorldPosition for world coords |
| `DigSiteBounds`, `NavBounds`, build-bounds `_center/_size` | item stubs / scene components | **object-local** world units | footprint libraries only |
| `States.GraphRect.*` | config/unlockable payloads | **graph-editor UI pixels** | NOT geographic — exclude from anything map-shaped |
| `TerrainMap/ObjectMap/AttributeMap` | LevelScenarioV2 plot layers | **tile indices** | ints; semantics partially known (EPlotTileType for plot tiles; terrain-paint enums unverified, G7) |
| locale term IDs | everywhere | n/a | signed int32 → I2 registry (piece-02 §2 mechanism, unchanged) |

Projection consequence for the site: one shared linear transform per
campus — `map_px = (world_xz − campus_min) × scale` — suffices for
plots, rooms, and items alike, because everything above shares the one
world frame; Leaflet simple-CRS in game-unit space works unchanged from
scout-001 §5.

## §11 Feasibility verdicts

1. **Per-campus overview maps — FEASIBLE from client data.** 16
   playable campuses each have: world bounds (§4), plot inventory with
   world-space rectangles (§3: e.g. MoonBase 61 plots), terrain tile
   maps, and the scenario join (§4). Geometry is measured; only the
   visual layer is authored (path D holds for imagery — §10 supplies
   raw material). The 26-scene ceiling survives as a *rendering*
   ceiling, not a data ceiling: scenarios cover remix/challenge
   variants beyond the 16 (51 total).
2. **Room-footprint plots — FEASIBLE.** 5,188 room records with grid
   anchors + explicit tile bitmaps + world positions (§3, §7). A room =
   its bitmap extruded at 2 u/cell; min-size rules from §2 annotate
   rather than constrain. Labels from `Rooms/*` terms (§9).
3. **Door/adjacency overlays — NOT DATA; DERIVABLE ONLY.** The class
   sweep found no doorway/door-definition type; rooms are player-built
   on plots, so shipped adjacency exists only where scenarios pre-build
   rooms. Derivable form: tile-bitmap contact edges between
   `RoomRecords` sharing a plot layer (pure geometry, mark
   `inferred: true, method: tile-bitmap-contact`). Navigation truth
   (`WaypointGraph`, NavMesh) is runtime-computed; only Knight ships 25
   waypoint seeds. Do not promise a door overlay in the spec.
4. **Item-placement pins — FEASIBLE at scenario scope.** 22,996
   placements with positions/rotations, 96.58% already name their
   definition (§3); residue needs the externals resolver (G4). Rules
   level (can-this-item-go-here) comes from §2's placement block +
   FloorAreaDefinitions. Live save-file parsing is out of scope for
