## §1 The decompile substrate — what "code" evidence exists here

This is an IL2CPP title, and that fact shapes every feasibility verdict
below. Measured:

1. **No method bodies exist anywhere in the corpus.** Every method in
   `dump.cs` is a signature + RVA (`public void .ctor() { }`). The
   Il2CppDumper output is declarations only; DummyDll assemblies carry the
   same metadata in binary form. Any *computed* gameplay constant that is
   not a serialized field exists only as machine code inside
   `GameAssembly.dll` (297 MiB), which stays on the client install
   (`data-acquisition.md` §S3) — it is not inside `extracted/`.
2. **The hottest logic is Burst-compiled besides.** Needs scoring and room
   scoring run through Unity ECS systems whose math jobs are Burst/native:
   `ESActionSatisfyNeedsScore` holds `GameAlgorithmsBurst.CFEHasFreeTime`,
   `CFESearchInteraction`, `CFEActionRoomScore` caches (dump.cs ~762006);
   `StaffBreakUtils.CalculateBreakNeed_00003B44$PostfixBurstDelegate`
   (~839040); `SimpleCurveEvaluatorExtensions.Evaluate_$BurstDirectCall`
   (~795147). Even a hypothetical IL-level decompile would not show these
   bodies as C#-like IL.
3. **What the code layer DOES give, completely:** the field schema of every
   serialized definition type (with offsets); every enum's full value set;
   `[SerializeReference]` polymorphic slot types; string literals
   (2.2 MB, incl. designer-facing mechanics prose); method names +
   addresses for every function (script.json) — the index a native pass
   would need.

Consequence: reconstruction splits into **(a)** surfaces whose constants
are serialized config payloads → faithfully reconstructable from corpus,
and **(b)** formula *shapes* whose arithmetic lives native → structurally
describable, numerically NOT inventable. §7 lists (b) explicitly so the
site never presents invented numbers as client truth.
