Verdicts: **whitespace tokenization works for 10 locales incl. ko**
(Korean spaces normally; the ko "CJK" column value is **Hangul-bearing**
rows — Han ideographs are negligible in ko, 11 chars total measured).
**zh-Hans/zh-Hant are unusable without character-bigram (or CJK segmenter)
indexing** — median 5-char strings with no spaces, only ~2.1 runs/row
(under-segmentation proven). **ja is mixed** — needs bigram fallback
alongside whitespace runs.

Cross-locale identity (text == en text): **ru 30.5%**, ja 16.5%, de 14.3%,
pt-BR 13.4%, fr 10.2%, zh/ko ≈1.3% — sizable untranslated-fallback layers
(§G5); proper nouns (item names) survive identically everywhere, which is
what makes cross-locale alias matching cheap.

Markup hygiene: en rows carry `<style="…">`/`<br>` tags on 6.0% of rows and
`{PLACEHOLDER}` braces on 4.8% — the indexer must strip tags and exclude
placeholder braces from tokens (same cleaning as the title-collision probe).

Collision dimension (informs shard-vs-single): within-locale duplicate
texts mapping to >1 key: en 1,570 · zh-Hans 1,668 · ko 1,702 · tr 1,625 …
(~9–11% of texts) — per-locale indexes remain many-to-many; no locale is
collision-free enough to invert text→entity naively.

Registry `locales[]` is **empty on all 15,675 rows** — verified against the
26 LanguageSource dumps themselves (`mTerms[].Languages` cells are genuinely
empty in-source; text ships per-locale bundle instead). Spec-R4's per-term
availability contract is therefore unmet by upstream data; search derives
availability by joining `locales/*.jsonl` directly (§G1).

## §4 Vocabulary stats + typo-tolerance feasibility

- Vocab per locale: **11,897 (en) … 28,594 (ko)** — table §3. Plus 3,224
  internal-id tokens (en side).
- Stopword candidates are measurable from the same run: en
  the/a/to/of/and/in/'s/you/for/it · fr de/la/le/à/un/les · de die/und/der/
  zu/das · es de/la/a/que/el · pt-BR de/o/a/para/e/que · tr bir/ve/için ·
  ru в/и/не/на · pl w/na/się/z/i · ja 構内放送-style domain words dominate
  after latin fragments. A frozen per-locale stoplist of ~10–20 entries is
  enough at this scale; or skip stopwords entirely (titles dominate).
- **Typo tolerance: trivially feasible.** Worst-case vocab 28.6k terms;
  Levenshtein-automaton / BK-tree / SymSpell over ≤30k terms answers d≤2
  queries in low milliseconds client-side; even a brute-force scan per
  keystroke is viable. No server infra required — the whole index fits in
  memory (payload math in §6).
- Edit-distance caveat for zh/ja: edit distance applies to bigrams, not
  whitespace words; bigram vocab for zh ≈ tens of thousands of 2-char
  sequences — still small.

## §6 Index-artifact shape options

Sizing inputs (measured): entity-relevant term texts (6,526 keys × 13
locales) = **9.45 MB raw** (~0.67–0.84 MB/locale, id+text+overhead);
full locale planes 23.1 MB. Titles-only plane MEASURED, not estimated:
display-name edges resolve to **2,059 distinct term keys** under the
pinned per-kind name fields (**2,532** with config `LocalisedName`/
`Title`/`DisplayName` + room `Name` added to the name class) →
**51–100 KB/locale raw text**, **≈0.16–0.21 MB/locale serialized** with
ids + JSON framing (brackets the verifier's 163–212 KB figure; difference
is framing/key-set definition only). Any Lunr/MiniSearch-style structure
lands within ~2–3× of its source text — i.e. **single-digit MB total, well
under 1 MB gzipped per locale shard**.

Options:

- **A. One combined index** (all locales, lang-tagged docs): simplest
  rebuild, one hash manifest; but every locale route ships everything
  unless the server slices it — wasteful given route-coded locale URLs.
- **B. Per-locale shards** `search/<loc>.jsonl` (+ `search/manifest.json`
  with sha256 + buildId + row counts): aligns with [DR-2026-08-20-locale-urls]
  routing (`/de/`, `/pt-BR/`…), en canonical at bare path, independent
  per-locale rebuild, ~1 MB/shard. **Recommended.**
- **C. Two-plane split inside each shard**: titles-only block (header
  instant box) + descriptions block (DB-page deep search) — lets the shell
  hydrate only the tiny title plane. Optional refinement of B; measure
  before committing.

Row grammar proposal (per doc): `{kind, id, termKey?, fieldClass(name|
description|alias), loc, text, weight}` — `kind` rides free on every edge,
so filter-by-kind costs nothing. Alias block carries: id tokens, `_dev`
strings, `DisplayName.mTerm` resolutions, (when §G2 closes) curated course
aliases.

Rebuild hooks: the runner already emits `.stage-stamps/<stage>.json`
(exitCode 0/2 semantics + script-hash deps) — a `search` builder should
re-run iff `relink`/`localisation` stamps changed, write sorted UTF-8 LF
JSONL + hash manifest byte-deterministically (pack conventions). **Exit-2
tolerance is mandatory:** relink's current steady state IS exit 2
(73 missing matrix cells, 1,137 dangling GUIDs, 5 registryMisses, bar-3
floor unmet `sourcesApplied=0` per RELATIONS/matrix) — search builds from
what landed and ledgers its own gaps; it never blocks on floors owned by
other pieces.

## §7 Feasibility verdicts

1. Instant filter-as-you-type over entity titles — **GO** (≤1 MB/locale,
   ≤29k vocab; client-side, zero infra).
2. Typo tolerance (edit distance ≤2) — **GO** at measured vocab sizes.
3. Per-locale shards — **REQUIRED**, not optional: 12 locales differ from
   en materially; route-coded URLs make shard-per-locale the natural seam.
4. CJK — **GO with conditions:** zh-Hans/zh-Hant require char-bigram
   indexing; ja requires bigram fallback; ko is standard whitespace.
5. Filter-by-kind — **GO**, free on the proposed row grammar.
6. Alias/id search — **GO**: 3,224 id tokens + 3,874 `_dev` strings are
   already on disk; zero new extraction needed.
7. Course-title search — **GO at ~86%, small residue** (§G2): mechanical
   conventions across four on-disk `_Name` families resolve 19/28 course
   defs (17/28 verifier basis); a ~7-entry token map reaches ~24/28;
   curated-alias residue ~4–7 rows. The 41 marketing courses still carry
   only dev-placeholder descriptions.
8. Item-title completeness — **GO via committed stubs** (§2): variations
   353/353 (`GameItem` int → Lite `DefinitionID`) and full definitions
   1,652/1,654 (`<id>_Lite` twin convention) reach `LocalisedName`. The
   joins are a pending relink EMISSION work item (AGENTS rule 8), not a
   data hole — search consumes them from stubs meanwhile.
9. Overall: the corpus supports a search experience at or above the
   observable competitor floor WITHOUT hosted search infrastructure.
