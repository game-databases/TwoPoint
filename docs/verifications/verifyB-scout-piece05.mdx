## Attack 1 — the "+5 locale drift" defect claim (scout §10 G1) → **BROKEN (inverts)**

The scout claims the localisation run-section counters "do not reconcile to
their own artifact by any documented rule" (logged rows = file lines +5 on
all 13 locales; totals 200,977 vs 200,912) and proposes an invariant pin
"`counter == artifact line count`" that would flag it today.

**Both halves of that framing are wrong. The counter reconciles exactly.**

1. **Code path** (`tools/stage4_localisation.py`): `rowsEmitted`
   increments on every emission **event**, including duplicate-key
   overwrites (lines 166–168 and 195–197 increment both `rowsEmitted` and
   the `duplicateKeysOverwritten` evidence counter); the emitted file
   writes one line per **distinct** key of the final dict (lines
   430–431). So by construction `logged rows − file lines =
   duplicate-key overwrite events ≥ 0`. The run-section line prints the
   event count under the label `rows` and never prints the computed
   `duplicateKeysOverwritten` counter (grep: defined at line 77,
   incremented twice, printed nowhere, persisted nowhere).
2. **Independent replay, zero free parameters.** I re-parsed the exported
   TextAssets (`extracted/harvest/textassets/localisation_assets_…/`, 25
   category assets per locale) with the exact `[i2t]` / `Term=text`
   grammar. For every one of the 13 locales: parsed events == logged
   `rows` **exactly** (de 15,450; en 15,670; ja 15,376; ko 15,462; ru
   15,427; …), parsed distinct keys == on-disk file lines exactly, and
   parsed skipped-empty cells == logged `skippedEmpty` exactly (de 227,
   en 7, ja 301, …). Total events = **200,977**, byte-for-byte the logged
   total.
3. **The systematic 5 is real data, not arithmetic error.** Exactly 5
   duplicate keys per locale, and the SAME five everywhere:
   `UI/General/PrestigeLevel`, `UI/Inspector/MedicalIssuesCured`,
   `UI/Inspector/PastoralIssuesCured`,
   `Characters/DLC_Hospital/Archetypes/Doctor_M_Name`,
   `Characters/DLC_Hospital/Archetypes/Nurse_F_Description`. The base
   registry shows the identical pattern from its own side: the 26
   LanguageSource dumps carry 15,677 walked terms with those same 5 dup
   Term keys → 15,672 distinct == base-overlay.jsonl lines; the log's
   `BASE-OVERLAY: rows=15677` vs header `baseOverlayRows: 15672` is the
   same events-vs-distinct pair the scout missed.

**Ruling:** neither the counter nor the file is wrong; the proposed B3 pin
("`rows` == wc-l") is itself defective. Correct contract: pin
`logged rows − file lines == duplicate-key overwrite events`, and route a
one-line fixer change to PRINT `duplicateKeysOverwritten` in the run
section. Residual true finding (downgraded to documentation): the label
`rows` on an event-count without the overwrite counter is what created the
illusion. The underlying I2 duplicate-term registrations are a genuine
measured client fact worth a contract note — but they are not a
counter↔artifact disagreement, and G1 as written ("either the counter or
the file is off") is false.
