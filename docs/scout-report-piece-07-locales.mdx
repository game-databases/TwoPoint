  exactly in both directions. No orphan key between registry and matrix.

  15402/275 over undeduplicated terms).

## §4 — Fallback semantics (base overlay + client behavior)

Measured facts:

1. The unnamed base bundle is a **master registry, not a fallback text
   table**: `base-overlay.jsonl` = 15,672 rows, **all with empty text**;
   its 26 sources define keys, `TermType`, `TermStatus`, descriptions,
   flags, and the 13-language column layout. Translations exist only in
   the 13 named bundles’ category TextAssets.
2. `base-overlay-report.json.compositionPolicy = "mixed"` with
   `differingTextSharedKeys = 15,665`. Honest reading (verified against
   the emitted rows): the classifier counts an empty base cell as
   “differing” from the English text — since ALL base cells are empty,
   “mixed” here encodes “base adds 7 keys English lacks; English adds
   nothing base lacks; no shared text comparison is meaningful”. The
   enum is still the contract (consumers read the field); the semantic
   caveat belongs in any downstream doc (§8 G7). Base-only keys vs en
   (7): `Buildings/BuildingGeneric_Description`,
   `Levels/DLC_Hospital/LakeHospital/Inbox_Fires_Title_Unused`,
   `UI/EmptyStringNoTranslate`, `UI/General/DLC/MSStore`,
   `UI/Messages/MissionStatus`, `UI/Messages/Suggestion`,
   `UI/General/NameSeparator`.
3. Each named bundle is **self-contained** for its language: 25 category
   TextAssets decoding to ~15.4k rows with only 215–301 empty cells
   skipped per locale (en just 7). Untranslated cells are *absent or
   empty*, never filled with another language inside the bundle.
4. **Client fallback machinery exists and is quotable; only its ORDER
   stays unprovable.** `dump.cs` declares the I2.Loc fallback API
   verbatim: `LanguageSourceData.TryGetFallbackTranslation(TermData,
   out string Translation, int langIndex, string
   overrideSpecialization, bool skipDisabled)` (~L546887),
   `LoadLanguageData(int languageIndex, string langData, …, bool
   useFallback, …)` (~L546872), and `LocalizationManager` static
   `GetTranslation(Term|TermID, …)` / `TryGetTranslation(…)` (~L547700+),
   beside the runtime classes (`LanguageSource`, `LanguageSourceData`,
   `LanguageSourceAsset`, `LocalizationReader`, `LocalizationManager`
   with `LoadLanguageAsync`/`SetLanguageAndCodeAsync`, `Localize`
   MonoBehaviour). Declarations carry no bodies, so the fallback ORDER —
   which language wins when the requested cell is empty — remains
   unproven at the data layer. What the data does prove: keys missing
   from a locale’s bundle demonstrably render in-game in that language,
   so resolution runs through exactly this declared fallback path. We do
   not assert its priority order.
5. **Our artifacts preserve whatever the client does**, because of the
   skip-empty discipline: no locale table ever borrows another locale’s
   text, and the matrix records absence truthfully. The site-side
   obligation therefore stands unchanged: per
   [localization-architecture.md §5.5](../../_foundation/localization-architecture.md)
   a missing locale page is omitted **or** rendered with an explicit
   localized “not yet translated” filler — never silently pivot-filled.
   Piece-07’s proof must pair every coverage percentage with the filler
   policy that covers the residue.

## §5 — Site-UI vs game-data split

The binding gate (“all locales the client ships”) governs **game data**.
The site’s own chrome is a separate i18n namespace
([localization-architecture.md §4](../../_foundation/localization-architecture.md)).
Measured inventory of both sides:

**Game-data side (client-provided, joinable):**

- 15,666-key string corpus, 52 top-level namespaces; entity-visible text
  flows through 10,964 hard `entity_locale` edges onto 5,850 entities.
- Game-UI namespaces reusable as game-faithful labels on our pages:
  `UI` (2,218 registry keys — 532 referenced by entities; 1,686 free;
  2,214 of them carry text in the emitted tables), `Input` (164),
  `UI_Settings` source (187), `General` (143). The
  piece-2 UI-link census additionally found **11,312 `I2.Localize`
  bindings** routing game-prefab text lookups to terms
  (`ui_link_coverage.jsonl` R5 census) — the game’s own UI is fully
  term-driven, so game-faithful component labels can be sourced, not
  invented.
- Free narrative text (9,146 unreferenced keys) feeds Guides/News/VO
  quotes in every locale.

**Site-chrome side (MUST be authored by the site; zero client
coverage):** navigation + labels, buttons, filters/sort options,
tooltips/help, empty states, error/404 pages, search placeholder +
results states, pagination, map controls, builder/planner/calculator UI
strings, UGC surfaces (sign-in, comments, corrections, screenshot
upload), consent/cookie banners, News/Guides editorial prose, SEO title
+ meta-description templates per locale, locale switcher, and the
“not yet translated” filler itself. Multiplied by 13 locales under the
ship-when-chrome-complete rule. None of these strings exist anywhere in
the client corpus — the client’s `UI/*` strings describe game screens,
not our site, and mixing the two namespaces is an explicit defect.

**Structural gap to close before the site consumes this (§8 G1):**
`extracted/relinks/locale_availability.jsonl` is **empty (0 rows)** —
the stage-5 sole-owner artifact honestly reports zero because the v1
name-based join found nothing and piece-2 §R4 rerouted consumers to
`entity_locale.jsonl`. But
[localization-architecture.md §5.4](../../_foundation/localization-architecture.md)
names that file the single source for cross-locale link rows, per-locale
sitemaps, and coverage stats. Either it gets regenerated from
`entity_locale` + the 13 tables (derivation is deterministic — this
report’s §2.2 math), or the pack declares the substitution in its spec.
Today the artifact the standard points at proves nothing; the relation
that proves it is `entity_locale.jsonl` + `locales/*.jsonl`.

## §6 — Competitor language UX bar

Method: WebFetch blocked network-side; wikily.gg fetched via curl with
`Claude-User` UA (polite, two requests); metaforge.app returned 403 to
curl and was rendered once through the sanctioned stealth headless-Chrome
tool (`web-browse browse.mjs`), two requests total.

- **wikily.gg** — full page-per-locale architecture, measured from
  served HTML/RSC payloads:
  - **24 hreflang locales** on the home page: `cs de en es es-la es-mx
    fr hu id it ja ko nl pl pt pt-br ru th tr uk vi zh-cn zh-hk zh-tw`
    (+ `x-default` → bare-path English). Locale in the URL (`/de/…`),
    pivot unprefixed — same contract as [DR-2026-08-20-locale-urls].
  - **Complete site-chrome i18n dictionary shipped per locale** in the
    page payload (EN `"no_results": "No results"` /
    DE `"Keine Ergebnisse"`; `"home"/"Startseite"`;
    `"select_game"/"Spiel auswählen"`;
    `"adding_comment"/"Kommentar wird hinzugefügt"`), with a payload
    `"locale"` marker — structurally the same chrome/game-content
    namespace split our standard mandates.
  - **Explicit partial-translation empty state**: a dedicated chrome
    string `"no_other_languages": "No other languages available yet."`
    — they surface missing languages rather than hiding or faking them.
  - Games sections exist under each prefix (`/de/ark-survival-ascended/`,
    `/de/once-human/`, `/de/subnautica/`, …) plus legal pages localized.
- **metaforge.app** — **single-locale English**. Measured on `/` and
  `/guild-wars-2`: zero `link[rel=alternate]` hreflang tags,
  `document.documentElement.lang = "en"`, no language switcher or locale
  prefixes anywhere in the DOM. No localization bar to clear.

**Bar statement for piece-07/site:** match wikily’s mechanics (locale
prefixes, full hreflang clusters, chrome dictionary per locale, honest
missing-language states) and exceed it where our standard is already
stricter — per-entity availability-driven link rows driven by a measured
artifact (not marketing), unique localized title/meta per locale, never
mixing locales on one page, and a declared filler policy. The client’s
13-locale roster (incl. `pt-BR`, `zh-Hant`, regional splits wikily also
carries) maps cleanly onto that shape.

## §8 — Gap ledger + open questions

**Gaps (each with concrete unblock):**

- **G1** `relinks/locale_availability.jsonl` empty (0 rows) while
  localization-architecture §5.4 makes it the single source for link
  rows/sitemaps/coverage. Unblock: regenerate from `entity_locale` +
  `locales/*.jsonl` (deterministic; §2.2 math) in the piece that builds
  the proof artifact — or record a pack-spec amendment naming
  `entity_locale.jsonl` as authoritative (piece-2 §R4 precedent).
- **G2** Course display-name join missing (0 name-role terms on all 69
  course rows; 28 courses lack any term). A pure id-suffix convention is
  PROVEN INSUFFICIENT: naive id-stem matching resolves **0/69** — real
  spellings diverge (`Course_Clowns`→`Clown_Name`,
  `Course_SpySchool*`→`SpySchool_Name`,
  `Course_PerformingArts`→`Music_Name`, `Course_Magic`→`Wizardry_Name`).
  Unblock: a MEASURED alias table (course id → term key), seeded from the
  marketing-campaign hard joins that already supply most base-course
  aliases (`Marketing/Courses/<alias>_Name`), emitted `inferred: true`
  with method; unresolved courses stay ledgered. Piece-08 ledgers the
  same hole for search with the same lever (best convention there
  resolves 12/28) — one alias input closes both consumers
  ([scout-report-piece-08-search.mdx §G2](scout-report-piece-08-search.mdx)).
- **G3** `registryMisses = 5`. Unblock: 3 closed by mapping `_dev`
  strings to `Code/<dev>` keys (verified present); 2 remain
  (`WantsMessage` on unused personal-goal items) — ledger or extend the
  walk to code-ref creation sites.
- **G4** Per-locale key holes (ja 295, ru 244, others 209–226;
  `Challenge/`+`Levels/` heavy). Unblock: none needed on data — apply
