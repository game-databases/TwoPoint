### F1 — MAJOR — The 122-basis PPtr-residue rule is pinned as policy but specified as neither scan nor schema

is non-null with an empty paired `*Reference` GUID field") but no
section defines HOW a conforming implementation finds those slots:

1. **Population:** which stub kinds are scanned (all nine? the same
   recursive `fields.*` walk as E1?), and what makes a field name

   vocabulary, 122 is not reproducible — two implementers produce two
   different ledgers, defeating the entire point of the pre-ruling.
2. **Enums:** the row shape carries `slotClass`
   (`external|same-file` — derivation rule unstated: fileId≠0 ⇒
   external?), `targetResolution` (NO value set anywhere in the spec),
   and `basis` (presumably the literal `122-basis` label — never said).
3. **Acceptance surface:** EC gates exit 2 on "every row within the
   declared `reason`/`slotClass` vocabularies", but the `reason`
   vocabulary for `_missing_icons.jsonl` is only partially declared

4. **No counters:** the pinned run-section block has keys for E1–E4/env

### F2 — MAJOR — Size-only renderdata matching is under-determined on this corpus; no pinned tiebreak and no ambiguity quota in the pixel-exact sample

**Location:** E4(1) (lines 240–249); E4(3) sample composition
(lines 258–264); §8 pairing-matcher bullet ("duplicate-size ambiguity →
deterministic tiebreak + counter"); M12 topology facts
(UI_Items_New 3×4096² pages, 1,099 slots; UI_Costumisation 400).

**Problem:** The working rule matches a sprite to its home page via its
OWN `m_RD.textureRect` SIZE against the owning atlas's
`m_RenderDataMap` entries. On this corpus same-size collisions are the
NORM, not an edge case: UI_Items_New packs 1,099 sprites across three
4096² pages plus a tail — dozens of slots share dimensions (the worked
example alone implies a family of 70×70 tab icons), and renderdata
entries for different pages carry identical WxH. A wrong pick yields a
same-dimension crop of the WRONG page region — garbage pixels that pass
every dimension check and ship silently unless the sprite happens to be
in the ≥20-sample cross-check lane. Yet:

- E4(1) itself specifies NO ambiguity handling — the only mention of a
  tiebreak lives in a TEST obligation bullet, which pins that one
  exists, not what it IS;
- the cross-check composition quotas (≥1 per route, ≥2 fractional, BC7
  sprite, two anchors, deterministic-stride remainder) never require an
  AMBIGUOUS-size sprite, so the tiebreak's correctness is untested by
  construction;
- no `ambiguousPairings` counter is defined in the run-section block.

**Fix shape:** In E4(1): pin the tieback order deterministically (e.g.
candidate entries ordered by `(pagePathId, entryIndex)` ascending, first
match wins), state it as CONTRACT not implementation detail, and add the
counter. Where the stronger discriminator is cheap, allow it explicitly
(renderdata entries carry their page texture pointer; a candidate whose
page bundle equals the sprite's home-bundle evidence may be preferred
before falling back to pure order). In E4(3): add a composition quota —
"≥3 sprites whose size-match was ambiguous" — so a wrong tiebreak
surfaces as `pixelMatchRate < 1.0` (exit 1) instead of silent wrong art.
In §8: the synthetic duplicate-size fixture then asserts the PINNED
order, not just determinism.

3. Therefore "the committed layer is the six text artifacts + rollup"
   ships as an empty git layer: a fresh clone gets the rollup and none

This is the same fragility that drove piece-05 to a repo-level
