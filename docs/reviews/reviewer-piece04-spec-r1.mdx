### F2 — MAJOR · the prerequisite taxonomy ⊆-assertion contradicts the spec's own census seeds (LevelPrerequisiteStars is not a Prerequisite subclass)

**Location:** F4 (seeds `HasCourseUnlocked ×50, UniversityLevel ×43,
LevelPrerequisiteStars ×26, ChallengePrerequisiteHasRoomUnlocked ×18,
DaysPassed ×17`), L1 `prerequisites.jsonl` ("Seed expectations (F4): …
Stars 26"; "the stage asserts the distinct `prerequisiteClass` set ⊆
the 24 names"), L1 `prerequisite-taxonomy.json`
(`{abstract:"Prerequisite", members:[24 names verbatim], source:
"class-hierarchy.jsonl + dump.cs census"}`), AC/L1 drift expectations.

**Problem (measured):** the 24-member `Prerequisite` taxonomy is real
and exact — `class-hierarchy.jsonl` enumerates exactly 24 rows with
baseType **`TPC.Prerequisite`** (namespaced spelling; a bare
`'Prerequisite'` equality match finds 0 rows), matching dump.cs 929626.
But the spec's own census seed counts a class outside that universe:
`LevelPrerequisiteStars` (×26) hangs off `TPC.LevelLiteConfig` carrier
rows (`Config_LevelLite_*`) and `LevelPrerequisiteStarsByLevelID` (×1)
off `TPC.MetagameConfig` — dump.cs declares both as
`: ILevelPrerequisiteData` (lines 880899/880924), a different family.
The true member is `PrerequisiteHasStarsInLevel : Prerequisite`
(dump.cs 929869), present in stubs ×13 on CareerChallenge carriers. So:

- if the walker selects by taxonomy membership, the "Stars 26" seed can
  never reconcile (it collects PrerequisiteHasStarsInLevel ×13), or
- if the walker sweeps typed blocks broadly, the ⊆ assertion fires a
  guaranteed first-run `DRIFT:` + gap row against data that has been in
  the corpus since day one — mislabeled "new content".

Either way two of the spec's own mechanical assertions fight each other,
and F4 additionally mixes naming conventions inside one seed line
(short prose names `UniversityLevel`/`DaysPassed`/`HasRoomUnlocked`
beside the stub spelling `LevelPrerequisiteStars`, whose full spellings
are respectively `PrerequisiteUniversityLevel`, `PrerequisiteDaysPassed`,
`ChallengePrerequisiteHasRoomUnlocked`).

**Fix shape:** (a) pin `prerequisites.jsonl` selection to classes whose
ancestry resolves to abstract `TPC.Prerequisite` per
class-hierarchy.jsonl (24 exact full spellings); (b) route
`LevelPrerequisiteStars`/`LevelPrerequisiteStarsByLevelID` to an
explicitly declared non-member sidecar (or second family) with their
measured counts 26/1 — ledgered, never silently dropped; (c) re-anchor
the "Stars" seed to `PrerequisiteHasStarsInLevel` ×13; (d) add the
short-name ↔ full-spelling map to F4/taxonomy so fixtures and code read
the same names; (e) note that baseType matching must be namespaced.

### F7 — MINOR · invention-guard escape-hatch bookkeeping is loose enough to have a bypass

**Location:** §3 L5 pass 1 vs the run-section key
`numericsByEscapeHatch:{copied, reconstructedFromCode, derivedArithmetic,
explicitNull}` and AC8's "outside the three legal escape hatches".

**Problem:** L5 declares THREE hatches ((a) reconstructed-from-code,
(b) derived-arithmetic, (c) explicit null) while the counter has FOUR
buckets including `copied`; AC8 then polices "the three". As written it
is unclear whether copied-and-matching numerics need an inline label
(they cannot — every copied float would need one), and hatch (b) accepts
any `method:"derived-arithmetic:<expr>"` string without requiring the
guard to verify the arithmetic — which makes (b) a laundering path for
precisely the numbers R4 forbids. The negative test (AC7) only exercises
an uncited number, not a mis-derived one.

**Fix shape:** state that copied-and-matching numerics are the default
audited path needing no inline label (hatch counting stays four-bucket),
align AC8's wording to "copied-matching plus the three labeled hatches",
and require hatch (b) expressions to be RECOMPUTED from their cited
inputs by the guard (counts/min/max/splits are mechanically checkable) —
non-recomputable ⇒ exit 1.
