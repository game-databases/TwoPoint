### F1 — MAJOR — Stage self-numbers as "eighth" against the canonical stage-index registry

**Location:** §3.3 ("`--list` enumerates EIGHT stages", line 158); §10
(`run_all.py / tools/tpc_common.py  # += eighth stage registration`,
line 494); §11 AC1 ("enumerates EIGHT stages ending `..., relink,
check-contracts`", lines 509–510); §14 ("eight-stage `--list`
ordering", line 581); §13 Q6 ("eighth-stage registration mutates
`--list` (seven→eight)", line 572); Revision-1 note ("non-emitting
eighth pipeline stage", line 635).

**Problem:** The orchestrator's canonical registry assigns contracts
stage index **10** (relink=6, maps=7, logic=8, locale-proof=9,
contracts=10) with explicit-10 naming, precisely because three sibling
specs each claimed "eighth stage". This spec makes that claim six times.
Worse, the ordinal assertions are mechanically unstable on their own
terms: AC1 hardcodes a TOTAL count plus tail sequence, which goes stale
the moment any of maps/logic/locale-proof registers (each insertion
shifts the tail and the count), guaranteeing a spurious acceptance
failure in a later piece.

**Fix shape (mechanical):** Adopt the canonical identity everywhere —
script `tools/stage10_check_contracts.py` (or equivalent explicit-10
naming), stage id `check-contracts`, registered at its canonical slot
after locale-proof=9. Replace every count/tail assertion with a
subset-and-order assertion ("`--list` contains … `relink` …
`check-contracts` in canonical order"), which survives sibling
registrations. Update Q6 from "arbiter confirms eight stages" to
"resolved by orchestrator registry — canonical index 10 recorded"; the
piece-01 Rev 8 note records the canonical registration, not an eighth
slot. Sanity-checked against `tpc_common.py::STAGES`: today seven
entries ending `("relink", "tools/stage6_relink.py", …)` — the additive
registration pattern claimed in §3.3 is real and unchanged.

### F2 — MAJOR — V-I8's declared-contributor list contradicts itself and changes piece-02 §5.7's pinned exit semantics

**Location:** §7 item 2 (lines 349–356); V-I8 row (line 395); coverage
matrix stage-5 L cell (line 253).

**Problem:** Two defects in one pin, and this is the incident-killer
validator:

1. **Internal contradiction on day one.** §7 declares the exit-2 iff-set
   to include `_absences.jsonl` and `_unmapped-families.jsonl`. Both are
   non-empty TODAY (2 and 768 rows per F13), yet §7's own enumeration
   says "Today: contributors = dangling 1,137 · unresolved pptrs 2,391 ·
   registryMisses 5 · outOfRoster 19 · floor-unmet". V-I8's check is
   "declared-contributor list == computed non-empty set" — as written,
   V-I8 FAILS on the current corpus at introduction. An implementer must
   silently pick one side, and the choice changes a pinned contract.
2. **Semantic regression vs piece-02 §5.7/AC7.** `_absences` and
   `_unmapped-families` are permanent-by-design ledgers (components are
   never entities; engine/primitive classes are honestly unmapped —
   there will always be 768-ish rows on any corpus). Adding them to the
   iff-set makes relink exit 0 UNREACHABLE forever. Piece-02 AC7
   explicitly rejects that design ("populated never demands zero gapped
   cells, ELSE R2's own missing-with-unblock doctrine could never reach
   exit 0"). Piece-02 §5.7's pinned condition is dangling-unresolved-open
   ∨ registryMisses>0 ∨ floor-unmet; the legitimate extensions here are
   `_uncontained_addresses` (new, RED-1) and the catalog-coverage counts.

**Fix shape:** Remove `_absences.jsonl` and `_unmapped-families.jsonl`
from the declared-contributor list (their honesty is already pinned by
V-S9 shapes + V-L2 sorts + the stage-5 exit contract; they do not need
exit-2 teeth), OR — if the piece genuinely wants them counted — say so
explicitly, correct the Today enumeration, accept permanent exit 2 as a
stated semantic change, and route a piece-02 revision note (see F10).
First option recommended; it keeps piece-02 §5.7 intact and the Today
sentence becomes true as written.

### F3 — MAJOR — The stage-2 "extended mini-report" is load-bearing for five validators and is specified nowhere

**Location:** §3.3 heavy-artifact policy (lines 159–166); V-I2 (line
389); V-R6 (line 441); V-X2 carve-out leg (line 403); V-L1 inputs (line
419); V-R8 inputs (line 443); §10 stage-2 amendment bullet (line 494).

**Problem:** The heavy-artifact policy bans parsing `catalog.json`
(397,431,200 B) in default runs and routes catalog-level pins through an
"EXTENDED emit-time mini-report" persisted inside stage 2. Five
validators consume it, including RED-1's entire green path. But the spec
never defines: the file's PATH (it appears nowhere in §10's layout), its
SCHEMA (V-S8's report-shapes list does not include it), or its CONTENT
budget. The consumers need incompatible depths: V-I2 needs the dupe-key
identity + both rows' bytes/hash; V-R6 needs keysTotal/kind sums/bundle
sets/dangling/outOfRoster; V-L1 and V-X2 need to answer "does address X
have a `bundle:null` catalog entry?" for arbitrary X (i.e., an
enumeration of bundle-null addresses or a per-address slice); V-R8's
bit-exact replay needs the full guid→[{bundle,address}] candidate map
for ≥5,584 distinct guids — verifyB replayed it with the real catalog
loaded, and nothing guarantees a summary-shaped report can reproduce
`resolveRate*` floats bit-exact. Left as-is, the CodeWriter invents the
artifact and the TestWriter cannot build V-R8's client-gated assertion
blind.

**Fix shape:** Pin the mini-report contract in this spec: name + path
(e.g. `extracted/addressables/catalog-mini-report.json[l]`, local-only),
exact top-level field list added to V-S8's report-shape row, and a
per-validator input ruling — cheap pins (V-I2/V-R6) read the
mini-report; deep lanes (V-L1 address slice, V-R8 guid index) either get
declared sections of the mini-report sized for the job (~54k guid rows
is fine as a local sidecar) or are marked CLIENT-GATED and read
`catalog.json` directly, streaming once, exactly as verifyA/verifyB did.
State which choice per validator; AC6's agreement test then has two
well-defined sides.
