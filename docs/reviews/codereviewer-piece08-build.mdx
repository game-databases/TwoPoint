## Findings

No CRITICAL, no MAJOR. Four MINOR findings — none blocks alone; all are
documentation/basis-label/hygiene gaps around an otherwise
digit-perfect build.

### F1 — MINOR — two contract re-pins live outside the spec file

(a) Rev 3 §S3.4 pins `ignoreKindCollisions: 320` as "distinct TITLE
TEXTS carried by more than one ENTITY ignoring kind". Measured on the
committed corpus that ENTITY basis yields **285**; the shipped basis
(carrying-INSTANCE multiplicity over RAW pivot texts, narrow edges +
consumed join instances) reproduces **320**. The implementation is right
and self-describing (`collisions.countingBasis` in-manifest, suite
docstrings, commit message), but a TestWriter implementing the spec
sentence as written measures 285 and fails the suite's hard
`== 320` assert. (b) §9's `≥4,500 non-en doc floor` is re-based to 2,800
in `test_N_real_shards_ac3_ac4` (justified: F16's prototype predates the
Rev-2 name-required + pivot-only pins; measured ~2,995–3,014), recorded
only in a test comment. This repo's discipline routes requirement
changes through revisions/rulings (AGENTS reading chain; RF-C precedent
graded a one-line residue a documentation pass). **Fix shape:** one Rev 4
documentation note recording (a) the instance-multiplicity collision
basis and (b) the join-state-aware floor re-base — no code change.

### F2 — MINOR — `devOnlyDocs` carries a different basis than its §S2 pin, unlabeled

Spec §S2 pins "G4 population: 779 item + 718 config + 46 metagame-node
name-fields". Re-measured from stubs: that triple reproduces ONLY as
name-class instances with `_termID == 0` regardless of `_dev` emptiness
(item 779 incl. 165 structurally-empty devs; config 718 incl. 27;
metagame-node 46 incl. 30) — i.e. a carrier-census basis, not a doc
count. The emitter instead publishes docs whose RESOLVED pivot name IS a
dev-fallback: `{item 614, config 692, metagame-node 16, room 2,
unlockable 6}` — arguably the more consumer-correct semantics for the
site's secondary-corpus merge, DRIFT-tracked and never asserted, so
nothing fails. But the divergence fires a permanent day-one DRIFT line
on the frozen seed corpus and, unlike `collisions`, carries NO basis
label in the manifest explaining it. **Fix shape:** add a
`countingBasis`-style label beside `universe.devOnlyDocs` (and beside the
SEEDS entry) naming both bases; fold the G4 re-pin into F1's Rev 4 note.

### F3 — MINOR — dead seeds: five §2 figures never reconciled

`SEEDS["f14TitleTextBytes"]`, `["planesBytes"]`, `["entityRelevantBytes"]`,
`["boneStringsConfigs"]`, `["narrowTitleEnResolvePct"]` are defined but
read by no `drift.check`. Their fresh measurements ARE emitted
(`sizes.f14*`, `localePlanesBytes`, `entityRelevantSerializedBytes`,
`configBoneStringCensus`) so the artifacts carry truth — but genuine
movement in these informational planes prints nothing, weakening the
module's own "seeds, never constants" posture for exactly the contrast
metrics. **Fix shape:** wire the five drift checks or delete the dead
keys; either is one commit.

### F4 — MINOR — latent deviation from the §S2 name-priority tie-break

The pin reads "localized name-class edge (first in sorted
`(fieldPath,dstId)` order)". `build_name_pools` stores
`sorted(set(names))` — lexicographic TERM-KEY order — and `resolve_name`
picks the first key that resolves in L. On the committed corpus the two
orders agree on every one of the 36 entities carrying >1 distinct
resolving name-class key (**0 divergences** — measured), so no emitted
byte differs today; the suite oracle additionally stops at the first
`(path,key)` edge rather than falling through to later name edges,
another latent divergence that also agrees today. Deterministic and
harmless now, but the pin exists precisely to keep two implementers
identical. **Fix shape:** carry the `(fieldPath,dstId)` order into the
pool's name candidate list (available before dedup) or record the
key-order basis beside the priority pin.
